01

Your first working loop

Build a small thing. Keep the feedback close.

Start with the included Signal Notebook: a command-line program that reads integer scores, validates them, and reports their mean. It has no third-party dependencies. You can follow every value from file input through a typed domain model to output.

shell
cd starter    # inside the rust-studio repository
# If this shell cannot find Cargo:
source "$HOME/.cargo/env"
cargo run -- scores.txt
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check

Expected program output, as recorded by the last verified build: 4 scores · mean 62.50. The full source is on the starter page. Open the starter folder in Zed. Rust support is built in; this project asks rust-analyzer to run Clippy for saved-file diagnostics. The terminal workflow works independently of editor setup.

Know the four names

rustup
Selects and installs toolchains and targets.
rustc
Compiles Rust source.
Cargo
Builds packages, resolves dependencies, runs tests and generates documentation.
rust-analyzer
Provides completion, navigation and editor diagnostics.

Three useful distinctions

A package is described by Cargo.toml. A crate is a compilation unit, such as a library or binary. A module organizes names inside a crate.

cargo check gives fast compiler feedback; cargo build also produces build artifacts. Use --release for performance measurements.

This edition targets Rust 1.100.0, released 12 November 2026. Every example on this page was compiled by rustc 1.100.0 (0ef1bc386 2026-11-09) when the site was built. A Rust program, studio-verify, checks each one against its declared outcome and refuses to publish a stale result. The starter pins the same compiler. 2024 is the edition name, not the year of your compiler. New projects should use edition = "2024"; upgrading an existing repository deserves its own migration and tests.

What changed in 1.100?

The never type ! is stable: you can name it, as in Result<T, !>, and std::convert::Infallible is now an alias for it. A function can now say in its signature that it cannot fail, and callers can write an irrefutable let Ok(value) = … with no Err arm. The release also stabilizes the Allocator API, core::mem::DropGuard, and smaller conveniences such as bool::toggle and str::trim_prefix.

Cargo now warns about unused dependencies by default (configurable under [lints.cargo]) and changes its internal build-directory layout. Final artifacts such as target/debug/signal-notebook stay where they were; this site's own build was checked against that.

Those are release notes, not prerequisites. The examples stay in safe, stable Rust.

Freshness boundary: the compiler results update whenever the pin changes; the prose is a researched snapshot as of 12 November 2026. Before future work, run rustup check, read release notes, and update deliberately. A toolchain pin changes only when you edit it.

03

Read the shape of Rust

Types make promises; expressions produce values.

let creates a binding. Add mut when that binding needs reassignment or mutable access. Shadowing with a new let creates a fresh binding and may change its type. A function declares parameter types and uses -> for its return type. Its final expression supplies the return value when you omit the semicolon.

u8 is an unsigned 8-bit integer; usize is sized for the target architecture and commonly represents lengths. String owns growable text. &str borrows UTF-8 text. The exclamation mark in println! denotes a macro. :: selects a path item or associated function; . calls methods or accesses fields.

The example's expect documents a known literal invariant. Do not copy that choice onto arbitrary user input: the error-handling chapter shows how to propagate failures.

04

The ownership observatory

Predict first. Reveal the compiler’s answer second.

Moving an owned String transfers responsibility for its allocation. A borrow gives access while the owner retains responsibility. Shared references permit observation; an exclusive reference permits mutation. References must remain valid, and conflicting access to the same data cannot overlap. Types such as integers implement Copy, so assignment copies their value instead of invalidating the source.

The six experiments, predict first

Decide for each one: does it compile? Open the verdict only after you have called it.

01 Move a String, then use the old name

The String moved to second. Using first afterward is rejected. Passing ownership does not implicitly clone the allocation.

The compiler rejects it: E0382.

02 Borrow the String instead

second borrows first. Both names can be used for this shared read, and first remains the owner.

03 Mutate before a shared borrow's final use

view is used after push. The shared borrow therefore conflicts with mutable access during push.

The compiler rejects it: E0502.

error[E0502]: cannot borrow `text` as mutable because it is also borrowed as immutable

  |                ----- immutable borrow occurs here
5 |     text.push('!');
  |     ^^^^^^^^^^^^^^ mutable borrow occurs here
6 |     println!("{view}");
  |                ---- immutable borrow later used here

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0502`.
04 Mutate after the borrow's final use

The final use of view is before push. The compiler can end that borrow, permitting the subsequent mutation.

It compiles and runs.

signal
signal!
05 Make a deliberate independent clone

clone creates an independent String. Mutation of second does not change first; copying the text has a cost.

It compiles and runs.

06 Copy an integer

u32 implements Copy. The assignment copies its value; no String allocation is involved.

It compiles and runs.

Reading a borrow error: find the original access, the conflicting access, and the later use keeping the borrow alive. Try shortening the borrow or separating computation from mutation. A clone is a valid design choice when two independent owned values are actually needed; it is not a universal fix.

This model covers ordinary references. Interior-mutability types such as RefCell and Mutex impose their own runtime rules; they do not erase the need to reason about access.

05

Lifetimes describe relationships

They never keep a value alive for you.

A lifetime annotation connects borrowed inputs and outputs. In this function, the returned reference is valid for a lifetime supported by both inputs. The compiler checks the actual call site. The annotation neither extends storage nor chooses which input is returned.

Here, “longer” means more UTF-8 bytes. If the caller needs ownership independent of the inputs, return a String. Returning a reference to a local String fails even if you write 'static.

Why doesn’t 'static repair a dangling reference?

The local allocation is dropped when the function returns. An annotation cannot prevent that. Return local as a String, or return a string literal that really does have static storage.

T: 'static means the type contains no borrowed references with shorter lifetimes. An owned String can meet that bound and still be dropped normally. It does not mean every such value lives forever.

06

Let the data model do work

A valid state should be easy to express.

A struct groups fields that belong together. An enum chooses one variant, optionally carrying data. This lets a completed job carry output while a queued job has none. An exhaustive match forces the code to account for every variant.

Option<T> expresses presence or absence using Some and None. Use it when absence is a normal possibility: the starter returns None for the mean of an empty input. Zero would claim a result that was never measured.

Library-team wisdom: distinguish meanings with types

The Rust API Guidelines recommend newtypes when values with the same representation have different meanings. In the starter, the private field in Score(u8) and its checked constructor keep values above 100 out of normal callers' hands. Keep the guarantee small and inspectable; do not encode every business rule into elaborate type machinery.

07

Give failures a useful shape

Expected failure is part of the API.

Result<T, E> contains either Ok(value) or Err(error). The ? operator returns early on an error, with supported conversion into the enclosing function's error type. It does not log or recover automatically.

The starter's library returns a concrete ParseScoreError with a line number; its CLI collects different failures behind Box<dyn Error> and prints one message at the boundary. Real applications often add context such as the operation and path, while avoiding sensitive payloads.

Practitioner note / Andrew Gallant

Make the panic policy about invariants.

Gallant argues that unwrap or expect can be appropriate when failure would reveal a programming bug, and in tests. Expected operational failures should use error handling. This is a reasoned policy, not a blanket license to panic. In this starter, invalid file contents return an error; tests use unwrap to make unexpected setup failure fail the test.

Apply it: for each expect, explain why failure is a bug. If the answer is “the user might type something else,” return a Result.

08

Borrow collections; consume with intent

Iteration is an ownership decision too.

Vec<T> owns a growable sequence. &[T] borrows a slice and lets functions accept arrays or vectors. For a Vec, iter() yields shared references, iter_mut() yields mutable references, and consuming into_iter() yields owned items. Read the receiver type: into_iter on a reference can yield references.

Iterator adapters are lazy. A consumer such as collect, sum, or a for loop drives the work. Use a plain loop when it communicates state changes more clearly. Collecting into Result<Vec<T>, E> can stop at the first error; the starter uses that behavior to reject invalid input.

Text has more than one length

String::len() counts bytes. chars() iterates Unicode scalar values, which are not necessarily visible characters. Rust disallows integer indexing into str; byte slicing requires UTF-8 boundaries and can panic. Prefer get(range) when boundaries are uncertain. For filesystem paths use Path / PathBuf and OS-native arguments rather than assuming UTF-8.

09

Abstract after the concrete case

Traits express behavior. They do not require a framework.

A trait defines shared behavior. An impl supplies it for a type. A generic bound or argument-position impl Trait lets the compiler specialize code for a concrete type. dyn Trait dispatches dynamically through a pointer, such as a reference or a Box. Not every trait is dyn-compatible.

Use mod for module structure, use for bringing names into scope, and pub deliberately at an API boundary. A library in src/lib.rs makes core logic reusable and easy to test; src/main.rs can concentrate on arguments, I/O, and exit behavior.

Practitioner note / Matthias Endler

Write code a tired colleague can trace.

Endler's “Be Simple” challenges unnecessary generics and indirection. The practical lesson is to make the domain operation visible and introduce abstraction when it resolves a concrete need. In this project, one parser and a small Score type are enough. A universal parsing framework would hide more than it explains.

Apply it: before adding a trait, name the second implementation or the boundary it isolates.

10

Choose the concurrency you actually need

Ownership continues across threads and tasks.

Send indicates that a value's ownership can cross thread boundaries. Sync means shared references can cross them safely. Arc provides atomic shared ownership, not automatic thread safety for arbitrary contents. Mutex provides synchronized access; short lock scopes make behavior easier to reason about. Scoped threads can borrow data because the scope waits for its threads.

Async is a scheduling contract

An async function produces a future. A runtime drives it; await can suspend the current task. A ready future need not yield, so merely writing await in a loop does not establish fairness. Async helps with concurrent waiting; it does not automatically make CPU work faster.

Practitioner note / Alice Ryhl

Do not occupy an executor thread with blocking work.

Ryhl explains why synchronous sleeps or expensive computation can stall other tasks in a cooperative executor. Current Tokio documentation supports moving bounded blocking work into spawn_blocking, limiting concurrent CPU jobs, and using dedicated threads for persistent blocking loops. Once a spawn_blocking closure starts, abort will not stop it.

Apply it: decide timeouts, cancellation behavior, queue limits and shutdown before spawning a task per input.

Start with synchronous code for a small CLI like this one. Add an async runtime when the workload needs concurrent I/O. No runtime dependency is required for the included lessons.

The senior-developer review desk

Tradeoffs are more useful than commandments.

Practitioner note / Nicholas Nethercote

Optimize the bottleneck you can demonstrate.

The Rust Performance Book emphasizes hot code, better algorithms and data structures, and measurements. Start with a release build and a representative workload. Change one thing, compare results, and retain the measurement that explains a surprising optimization. Reducing unnecessary work can matter more than making a tiny operation clever.

Apply it: measure the starter on a large file before replacing its readable parser. If memory becomes the issue, investigate streaming I/O before low-level tricks.

Questions worth asking in review

  • Who owns this data, and how long must it live?
  • Can this invalid state be constructed outside its module?
  • Does the caller have enough context to handle this error?
  • Are allocation, I/O and locking visible where they matter?
  • What does cancellation leave partially done?
  • Which measured requirement justifies this abstraction?

Keep expert advice in context

The named notes summarize each author's published reasoning. They are not quotes, a consensus vote, or evidence that one technique always wins. The examples and review questions are this primer's synthesis.

Unsafe, procedural macros, pinning internals and FFI belong to later study. Unsafe requires proving obligations that the compiler no longer checks; it does not switch off ordinary type checking.

Four sessions to a useful Rust habit

Each exercise changes observable behavior.

01 / Ownership, 30–45 minutesRun all six observatory experiments. Explain why the original String is unavailable after a move but remains usable after a borrow. Read the first compiler error before changing code.
02 / Domain model, 45–60 minutesAdd a maximum(&[Score]) -> Option<Score> function. Test empty input, one value, duplicate maxima and endpoints. Keep the Score field private.
03 / Error behavior, 45–60 minutesAdd support for lines beginning with # as comments. Preserve original line numbers in failures. Test CRLF, leading whitespace, comments and malformed input.
04 / Measurement, 60 minutesCompare whole-file reading with a BufRead-based streaming version on generated non-sensitive data. Record release timing and peak memory. Decide whether the complexity buys enough.
Retrieval practice: five questions to answer aloud
  1. When does assignment move a value, and when does it copy?
  2. Why does annotating a lifetime not extend an allocation's life?
  3. What does ? do when it sees an Err?
  4. Why can a successful audit still leave a program vulnerable?
  5. Why can an async function still block the executor?

Tick these off on paper or in your editor; nothing on this page tracks you.

Maintain a kit you understand

One owner per tool. Pins for projects; deliberate updates.

Rustup owns your toolchains and components. Pick one owner for each Cargo extension: Homebrew bottles for nextest, Bacon, cargo-deny and cargo-llvm-cov, say, and cargo install --locked for the rest. Avoid installing duplicate copies of the same executable through different managers; which -a cargo-nextest shows when you have.

shell
rustup check
rustup update stable --no-self-update
brew outdated cargo-nextest cargo-deny bacon cargo-llvm-cov
# Apply upgrades when you are ready:
brew upgrade cargo-nextest cargo-deny bacon cargo-llvm-cov
# Inspect Cargo-managed utilities separately:
cargo install --list

For a new dependency, verify its crate name, upstream repository, maintainer activity, features, license and build behavior before using cargo add. Build scripts and procedural macros run code during builds. Use cargo tree -e features to inspect why code is present. Keep Cargo.lock with this application and use --locked in repeatable checks.

cargo install --locked uses the package's supplied lockfile when available. That improves reproducibility but may also preserve older dependency versions. It is not an audit. Dependencies belong in each project's Cargo.toml, rather than a global pile of libraries.

Extensions when the project calls for them

Nightly + Miri for additional undefined-behavior checking; cargo-fuzz for fuzzing; a benchmark harness for statistically informed timing; platform SDKs for cross-compilation. These are optional follow-ons, not part of this kit. Target libraries alone do not supply every linker, runtime or deployment tool.

Removal is piecemeal: Homebrew tools can be removed individually with brew uninstall; an exact toolchain can be removed with rustup toolchain uninstall 1.100.0 after changing any project that pins it. To move this kit to a new release, edit both rust-toolchain.toml pins, run cargo run -p studio-verify -- write, and read the diff: it shows exactly which compiler messages changed.
